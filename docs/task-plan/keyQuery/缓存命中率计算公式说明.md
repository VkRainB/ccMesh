# 模型缓存命中率（Cache Hit Rate）计算说明

本文整理 AI 网关 / Agent 客户端里「缓存命中率」的计算公式：统一推荐式、各渠道 usage 语义、sub2api / DeepSeek Harness / ZCode 的实际算法、数值例子，以及不要踩的坑。命中率一律按 **token 加权**，不用请求次数。

读者：要在本仓库（tauri-gateway）或对照其它产品复核「缓存命中率」数字的开发人员。

---

## 1. 结论（先看这个）

**推荐公式**（先把各渠道 usage 归一成互不重叠的三桶，再除）：

```text
Cache Hit Rate = cache_read / (input_net + cache_read + cache_write)
分母为 0 时：不展示，或记 0（不要当成「0% 命中」）
```

| 符号 | 含义 | 常见字段 |
|---|---|---|
| `input_net` | 未命中缓存的新输入（净输入） | Claude `input_tokens`；归一后的 OpenAI / DeepSeek `input` |
| `cache_read` | 从 prompt / KV cache 读出的 token | Claude `cache_read_input_tokens`；OpenAI `cached_tokens`；DeepSeek `prompt_cache_hit_tokens` |
| `cache_write` | 写入缓存的 token（创建缓存） | Claude `cache_creation_input_tokens`；OpenAI / DeepSeek 通常为 0 |

这是 **prompt 侧** 的命中率：分子、分母都不含 `output` / `reasoning`（reasoning 是 output 的子集，不要再加一遍）。

**不是：**

- `有缓存的请求数 / 总请求数`
- `cache_read / (input + output + cache)`（输出从未被缓存承接）
- `cache_read / (cache_read + cache_write)`（OpenAI / DeepSeek 几乎没有 write，会算成 100%）
- 未归一化时对 Claude 做 `cache_read / input_tokens`（净输入当分母，命中率会超过 100%）

**怎么聚合：** 先对时间窗 / 会话 `SUM` 各桶，再相除（token 加权）。一次 1M token、90% 命中的请求，会压过一百次 1k token、0% 命中的请求。这不是「每条请求命中率再平均」。

---

## 2. 为什么必须先归一：OpenAI / Claude / DeepSeek 行为不同

上游 `usage` **不是同一套语义**。不归一就套同一条除法，数字会对不齐，甚至超过 100%。

### 2.1 对照表

| | OpenAI Chat / Responses | Anthropic Claude | DeepSeek Chat Completions |
|---|---|---|---|
| 总输入叫什么 | `prompt_tokens` 或 `input_tokens` | 没有单独「总输入」字段 | `prompt_tokens` |
| 总输入是否含缓存命中 | **含**。`cached_tokens ⊆ prompt_tokens` | **不含**。`input_tokens` 只有新鲜输入 | **含**。官方：`prompt_tokens = hit + miss` |
| 命中字段 | `prompt_tokens_details.cached_tokens` 或 `input_tokens_details.cached_tokens` | `cache_read_input_tokens` | `prompt_cache_hit_tokens`（V4 同时给 `prompt_tokens_details.cached_tokens`） |
| 未命中字段 | 总输入 − 命中 | `input_tokens` 本身 | `prompt_cache_miss_tokens` |
| 写缓存字段 | 一般不返回（Codex 偶发 `cache_write_tokens`） | `cache_creation_input_tokens`（可再拆 5m / 1h） | 官方不返回写缓存计数 |
| 直接用「命中 / 总输入」 | 可以，且 ≤ 100% | **不行**（`命中 / 净输入` 常 > 100%） | 可以，且应等于 `hit / (hit + miss)` |

### 2.2 归一成互不重叠三桶

各产品落地时都做了同一件事：OpenAI / DeepSeek 的「总输入」先扣掉命中，得到净输入，再与 Claude 对齐。

**OpenAI（sub2api / tauri-gateway）：**

```text
cache_read = cached_tokens
input_net  = max(prompt_tokens - cache_read, 0)
cache_write = cache_creation_input_tokens   # 通常 0
```

**DeepSeek Harness `mapUsage`（`packages/llm/llm-deepseek/src/translate.ts`）：**

```text
cache_read = prompt_tokens_details.cached_tokens ?? prompt_cache_hit_tokens
input_net  = prompt_tokens - (cache_read ?? 0)     # 即 miss
cache_write 不映射（DeepSeek 不上报）
```

注释写明：线上 `prompt_tokens` **包含** cache hit；Harness 的 `TokenUsage` 约定是 **互不重叠**。

**Claude：** 已经是互不重叠，不要再减。

```text
input_net   = input_tokens
cache_read  = cache_read_input_tokens
cache_write = cache_creation_input_tokens
```

归一之后，三条渠道共用第 1 节公式。分母就是这次请求（或这段汇总）的全部 prompt token。

### 2.3 在「未归一」的原始字段上怎么除

若你手里还是上游原始 JSON，等价写法是：

```text
# OpenAI / DeepSeek（总输入已含命中）
rate = cached_or_hit / prompt_tokens

# Claude（总输入要自己加）
rate = cache_read / (input_tokens + cache_read + cache_creation)
```

判断该用哪条：若出现 `cache_read > prompt/input`，一定是 Claude 语义，必须用第二条。OpenAI 按定义不会出现「命中大于总输入」。

## 3. 各项目实际怎么算

### 3.1 DeepSeek Harness（dsh）

源：<https://github.com/deepseek-ai/deepseek-harness>

会话级（作曲栏 Token 用量药丸，`StatsPills.tsx`）：

```text
billedInput = uncachedInputTokens + cacheReadTokens + cacheWriteTokens
cacheHitPercent = formatCacheHitPercent(cacheReadTokens, billedInput)
```

即：

```text
rate = cache_read / (input_net + cache_read + cache_write)
```

与第 1 节推荐式相同。`uncachedInputTokens` 就是归一后的净输入。

Turn 级（`TurnUsagePanel.tsx`）分母写成 `totalTokens - outputTokens`。在 `turn-usage.ts` 的校验下，这等于「精确 prompt 合计」，有 write 桶时与上面三桶之和一致。

TUI 页脚设计说明（已归档，公式仍适用）：

```text
cacheHitRate = round(cacheRead / (input + cacheRead + cacheWrite) * 100)
尚无计费输入时返回 undefined，整段不展示（不显示假的 0%）
```

设计里明确否决过：

- 分母含 output → 无意义地压低命中率
- 分母去掉 cacheWrite → 写入那一轮会虚高
- 空会话显示 0% → 那是 0/0

展示细节：`formatCacheHitPercent` 在「接近但不是 100%」时不会四舍五入成 100%，而显示 `99.9…`。满命中才显示 `100`。

DeepSeek 官方 usage 关系（[Context Caching](https://api-docs.deepseek.com/guides/kv_cache/)）：

```text
prompt_tokens = prompt_cache_hit_tokens + prompt_cache_miss_tokens
官方命中率    = prompt_cache_hit_tokens / prompt_tokens
```

dsh 扣掉 hit 得到 `input_net` 之后，`cache_read / (input_net + cache_read)` 与官方式相同（write=0 时）。

### 3.2 sub2api

趋势图 `TokenUsageTrend.vue` 在前端用日/小时聚合点现算，后端只 `SUM` token，不算命中率。

**GitHub 主线（PR [#2682](https://github.com/Wei-Shaw/sub2api/pull/2682)，2026-05-22 已合并）：**

```text
totalPrompt = input_tokens + cache_read_tokens + cache_creation_tokens
rate%       = totalPrompt > 0 ? cache_read / totalPrompt * 100 : 0
```

落库时 OpenAI 路径已把 `prompt_tokens` 扣成净输入（`openai_gateway_service.go` 的 `actualInputTokens`），因此这里的 `input_tokens` 就是 `input_net`。与 dsh / 第 1 节一致。

**本机 `e:\myCode\sub2api` 仍是旧式：**

```text
rate% = cache_read / (cache_read + cache_creation) * 100
```

OpenAI 几乎不返回 `cache_creation`，旧式会把「有任何 cache_read」显示成 **100%**。实现或对照数字时以 GitHub 主线为准。

### 3.3 ZCode 用量快照

`buildAppUsageSnapshot`（见 `ZCode使用统计数据存储与读取分析.md`）：

```text
effectiveInput = inputTokens > 0 ? inputTokens : (cacheCreation + cacheRead)
cacheHitRate   = effectiveInput > 0 ? cacheRead / effectiveInput : 0
```

这里的 `inputTokens` 在实测快照里是 **含缓存的总输入**，不是 Claude 净输入：

```text
inputTokens      = 156_351_369
cacheReadTokens  = 153_608_640
cacheHitRate     = 0.982457915…   # 恰好等于 153608640 / 156351369
```

若误把该 `inputTokens` 当成净输入再套第 1 节公式，分母会变成「净输入 + 命中」，命中率会被算小。ZCode 这条是 `命中 / 快照 inputTokens`，且该样本的 input 已含命中。

### 3.4 本仓库 tauri-gateway

目前 **没有** 对外展示 Cache Hit Rate。`TokenUsage` 已经按互不重叠四桶归一（`src-tauri/src/modules/usage.rs`）：

```text
OpenAI / Responses: input = max(prompt_tokens - cache_read, 0)
Claude:             input = input_tokens（不再减）
合计:               input + output + cache_creation + cache_read 不双重计数
```

若以后做命中率，应直接用第 1 节公式，不要再对 `input` 减一次 `cache_read`。

## 4. 数值例子

### 例 A：OpenAI / DeepSeek 风格（总输入已含命中）

上游：

```text
prompt_tokens = 2000
cached_tokens / prompt_cache_hit_tokens = 1500
cache_creation = 0
completion_tokens = 100
```

归一：`input_net = 500`，`cache_read = 1500`，`cache_write = 0`

```text
命中率 = 1500 / (500 + 1500 + 0) = 75%
等价   = 1500 / 2000 = 75%
```

旧 sub2api 式：`1500 / (1500 + 0) = 100%` ← 错。

### 例 B：Claude 风格（净输入 + 读 + 写）

上游：

```text
input_tokens = 200
cache_read_input_tokens = 500
cache_creation_input_tokens = 300
output_tokens = 50
```

```text
命中率 = 500 / (200 + 500 + 300) = 50%
```

错误算法：

| 错法 | 结果 | 原因 |
|---|---|---|
| `500 / 200` | 250% | 净输入当分母 |
| `500 / (200 + 50)` | 200% | 把 output 算进去还用错了分母 |
| `500 / (500 + 300)` | 62.5% | 丢掉新鲜输入，写入轮虚高 |

### 例 C：DeepSeek 官方字段（与例 A 同构）

```text
prompt_tokens = 12000
prompt_cache_hit_tokens = 9000
prompt_cache_miss_tokens = 3000
completion_tokens = 950
```

校验：`9000 + 3000 = 12000`，`12000 + 950 = 12950`。

```text
命中率 = 9000 / 12000 = 75%
```

`reasoning_tokens` 若出现在 `completion_tokens_details` 里，已含在 950 中，不参与命中率。

### 例 D：dsh 写入那一轮（分母含 cache_write）

```text
uncached = 400
cache_read = 600
cache_write = 200
output = 80
```

```text
命中率 = 600 / (400 + 600 + 200) = 50%
```

若去掉 write：`600 / 1000 = 60%` ← 把「为填缓存付费的输入」当成命中，虚高。DeepSeek 当前 write=0，这条主要影响 Claude / 部分 Codex。

### 例 E：会话汇总（token 加权，不是请求平均）

| 请求 | 净输入 | 命中 | 写缓存 |
|---|---:|---:|---:|
| 冷启动 | 8000 | 0 | 8000 |
| 热请求 × 9 | 200 | 15800 | 0 |

```text
SUM 净输入 = 8000 + 9×200 = 9800
SUM 命中   = 0 + 9×15800 = 142200
SUM 写入   = 8000
命中率     = 142200 / (9800 + 142200 + 8000) = 142200 / 160000 = 88.9%
```

若按请求次数：1 次 0% + 9 次约 98.8%，平均约 88.9% 只是碰巧接近；把冷启动改成 100k 净输入后，token 加权会明显低于「请求平均」。产品指标用 token 加权。

### 例 F：空数据

```text
全部为 0 → 0/0
dsh：不展示
sub2api 主线：0
ZCode：0
```

不要对用户说「命中率 0%」，那是「还没有 prompt」。

## 5. 注意事项

1. **先认渠道语义，再做除法。** 同一条 `input_tokens`，Claude 是净输入，OpenAI Responses / DeepSeek 是含命中的总输入。本仓库 `usage.rs` 已把后者扣成净输入；对归一后的 `TokenUsage.input` 不要再减 `cache_read`。
2. **分母是全部 prompt，不是全部 token。** 不要加 output / reasoning。
3. **cache_write / cache_creation 进分母、不进分子。** 写入是 miss（为后续命中付费），不是 hit。
4. **不要用「有 cache_read 就算命中一次请求」。** 部分命中（例如 256 token 对齐后只命中前缀）在 token 式里是 40%，在请求式里会变成 100%。
5. **OpenAI 旧式 `cache_read / (cache_read + cache_creation)` 不可用。** 没有 creation 时恒为 100%。
6. **混渠道汇总必须先归一。** 把 Claude 净输入和 OpenAI 总输入加在一起再除，分母口径不一致。
7. **上游是尽力而为。** DeepSeek 文档写明不保证 100% 命中；缓存按前缀匹配、有粒度（社区测量约 256 token 一块）、会过期。命中率为 0 也可能是 TTL、换账号、换模型、system/tools 顺序变了，不一定是公式错。
8. **流式不要重复计数。** dsh / 本仓库都是「同一步的 streaming usage 被最终 message usage 替换」。命中率用最终桶，不要把 chunk 和收尾加两次。
9. **展示不要把 99.x% 四舍五入成 100%。** dsh 为此做了专门格式化。
10. **ZCode 的 `inputTokens` 口径以快照为准。** 设计文档写「与 Claude 净输入一致」，但实测 `cacheHitRate = cacheRead / inputTokens` 且 input 已含命中。对接 ZCode 数字前先用 `cacheRead ≤ input` 验证口径。

## 6. 本仓库若要实现时的落点

归一已经在 `TokenUsage`（`input` / `output` / `cache_creation` / `cache_read`）完成。命中率只应是：

```text
denom = input + cache_read + cache_creation
rate  = denom > 0 ? cache_read / denom : null
```

对请求日志做窗口汇总时，对四元组 `SUM` 后再除，与 sub2api 趋势图、dsh 会话药丸相同。

| 按 token 加权、不用请求次数 | **高** | 上述实现均对 token 求和再除；请求数字段未进入公式 |

| Claude：`input_tokens` 不含读/写缓存 | **高** | Anthropic 文档；本仓库 / sub2api 均按分列存储 |
| DeepSeek：`prompt_tokens = hit + miss` | **高** | [官方 Context Caching](https://api-docs.deepseek.com/guides/kv_cache/)；dsh `mapUsage` 注释 |
| dsh 会话命中率实现 | **高** | 已读 `StatsPills.tsx`、`token-format.ts` 源码 |
| dsh Turn 分母 `totalTokens - outputTokens` | **高** | `TurnUsagePanel.tsx`；`turn-usage.ts` 要求其 ≥ 已知 prompt 桶之和 |
| sub2api 主线公式 | **高** | GitHub `TokenUsageTrend.vue` + PR 测试（75% / 50% / 0） |
| 本机 sub2api 仍为旧公式 | **高** | `e:\myCode\sub2api\...\TokenUsageTrend.vue` 仍是 `read/(read+creation)` |
